# Mira v0.1.0-beta.1 Release 方案

- 状态：Draft Release Candidate
- 日期：2026-08-31
- 发布形态：GitHub Draft PR 合并后创建 prerelease
- 目标用户：愿意在本地运行 Standalone Web 版本并反馈核心工作流的早期用户

## 1. 发布目标

本候选版本验证 Mira 的单一产品主线：用户在画布上组织内容，通过 Transformation 生成成果，把已验证路径保存为方法，并在新材料上复用。Release 不承诺无人值守自动化，也不引入第二套流程运行器。

建议版本号为 `v0.1.0-beta.1`。仓库尚无正式 tag，因此先用 prerelease 收集安装、模型连接、长画布和真实任务反馈；通过发布门禁后再决定 `v0.1.0`。

## 2. 包含范围

- Card / CardVersion、Transformation、Run、stale 与 Candidate 安全语义。
- 紧凑可移动的 Transformation 卡、线性网格和内容分支聚焦。
- Context dock 的`生成 / 先放步骤`。
- 下游`运行到这里`：向上检查依赖，跳过最新结果，只生成空目标或 stale 步骤，并在指定目标停止。
- 从已验证路径保存 WorkflowTemplate；通过画布连线绑定具名输入并添加 WorkflowPlan。
- 默认模型与单步模型覆盖；Standalone 网页可配置 Kimi K3 或 OpenAI-compatible 服务。
- Standalone Node host 与可选 DSH/Cordis adapter。

## 3. 不包含范围

- Electron 或其他 macOS 桌面薄壳。
- 无目标的 run-all、后台 trigger、条件分支或独立 Action/chain runtime。
- 数据导入、导出 UI、云同步、多人协作和跨进程写锁。
- API Key 持久化到仓库、Board、Run、Workflow 或 LaunchAgent plist。
- 用户 `boards-v2/`、`runs-v2/`、`workflows-v2/` 数据作为 Release 源码提交。

## 4. 发布门禁

合并和打 tag 前必须全部通过：

```sh
pnpm test
pnpm exec tsc --noEmit
pnpm build
pnpm build:bridge
git diff --check
```

可见 UI 必须在 1440px 和 390px 验证网格、转化命令、详情 sheet、焦点、遮挡和横向溢出。Run、Candidate、Workflow 和模型设置必须包含 Bridge 集成测试；至少使用一个真实模型完成一次两步`运行到这里`狗食。

当前证据见 [`../validation/2026-08-31-release-candidate-validation.md`](../validation/2026-08-31-release-candidate-validation.md)。真实 Kimi 狗食未完成前，本版本只能保持 Draft PR / prerelease candidate，不能标记为 stable。

## 5. 数据与升级

- 发布前备份 `boards-v2/`、`runs-v2/` 和 `workflows-v2/`，不批量改写用户数据。
- 当前 schema 仍为 Board v2；新字段保持可选，旧 Board 缺少 Transformation 坐标、`lastAppliedRunId`、`modelId` 或 Workflow inputs 时走兼容默认值。
- Standalone 与 DSH/Cordis 不能同时写同一 workspace。
- 构建产物由发布流程生成，不提交 `dist/` 或 `dist-bridge/`。

## 6. 回滚

1. 停止 Standalone 服务，保留业务数据与日志。
2. 切回上一个已验证 commit/tag，重新执行前端和 Bridge 构建。
3. 启动服务并只读检查 Board、Version、Run 与 Candidate 可达性。
4. 若新版本已经写入数据，不自动降级或删除；从发布前备份恢复到独立临时 workspace 验证后，再由操作者决定恢复路径。

## 7. Release Notes 草案

### Highlights

- 用更轻的内容画布组织材料、成果与可复用方法。
- 在任一下游步骤点击`运行到这里`，Mira 自动跳过最新结果，只更新真正受素材变化影响的步骤。
- Transformation 成为可移动的紧凑卡片，可单步查看来源、模型、历史和 Candidate。
- 方法通过用户连线绑定输入，添加到画布后保持零自动 Run。

### Safety

- 人工编辑不会被模型结果覆盖；冲突结果进入 Candidate。
- 失败、停止、缺少素材、Candidate 或运行信息不确定时，后续步骤不会启动。
- 删除结构不级联删除 Card、Version 或 Run。

### Known Limitations

- 网页模型设置仅保存在当前服务进程；重启后需要环境变量或重新设置。
- Kimi K3 需要有效 API Key；Release 不携带任何供应商凭据。
- 当前没有云同步、多人协作、导入导出 UI 或跨进程写锁。

## 8. GitHub 发布步骤

1. 将产品代码、测试、权威文档和本 Release 方案提交到 feature branch；排除用户 Board/Run 数据。
2. 推送分支并创建 Draft PR，附完整测试与浏览器证据。
3. 完成真实 Kimi 两步狗食，更新验证记录并将 PR 标为 Ready for review。
4. 合并后创建 annotated tag `v0.1.0-beta.1`。
5. 创建 GitHub prerelease，使用本文件的 Release Notes，并附安装、模型配置和数据备份说明。
