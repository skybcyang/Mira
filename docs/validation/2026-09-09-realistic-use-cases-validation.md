## 场景与制作方式

软件案例以需求为中间成果，分别分出验收与内测说明；人工更新需求和内测说明后，新增 F-19 到验收来源，旧清单保持 stale。稳定阶段手动保存一个检查点，并验证绑定 Markdown 文件随人工编辑写回。

阅读案例按主题组织，包含书中片段概括、带 pool 出处和标签的生活观察、独立未解问题、人工实践与两版回看；仅一次三来源转化。研究案例让两种竞争解释共享 O-02，O-03 作为反例参与解释 B，两支汇合为下一轮研究决定。

写作通过计划 API 创建三步结构，逐步产生并检查非空成果，提取一个包含两个具名输入的 WorkflowTemplate。随后在生成尚未完成时保存人工正文，再释放预写结果，正常写回机制产生 Candidate，保留人工 v2；下游核查变为 stale。

所有内容为人工编写的原创或虚构演示材料。使用独立临时 workspace 和随机本地端口，通过生产 Node Host/HTTP API 创建与运行。临时适配器标记为 `local-demo / authored-example`，进度明确为载入人工演示文本；没有连接或评价真实模型，没有接触用户实际画板。临时脚本不接入产品运行路径。

## 浏览器与图片

使用 Chrome 访问临时 Node Host 的当前 React UI。四张全景为 1920×1150 CSS 像素、1.5 倍截图；近景采用 1440×1000 或 1440×800，版本面板与比较弹窗为实际元素截图。没有改 DOM 伪造功能或状态。

- 全景：需求支线、主题读书、竞争解释、改稿中的三步计划。
- 近景：检查点比较、灵感搜索与标签、转化来源与处理要求、Candidate 并排阅读。
- 390×844：打开 Candidate，确认正文与采用入口可见；Tab 焦点保留在比较弹窗内，关闭后退出弹窗，页面无横向溢出。
- 最终截图与窄屏运行：无 pageerror、console warning/error；逐张目视检查文字、连接、裁切与遮挡。

临时浏览器脚本初版误把 search input 当作 textbox，并漏掉运行详情到比较弹窗的第二次点击。按当前组件的真实可访问角色和按钮修正脚本，最终完整重跑通过；没有修改生产 UI。

README、教程、案例与下载说明使用现有 React Markdown + GFM 渲染，在 1440px 和 390px 下检查。155 个本地链接及锚点有效，图片均加载成功，页面无横向溢出；表格和代码块在自身区域滚动。本项为本地 Markdown 渲染验证，不替代 GitHub 页面验收。
