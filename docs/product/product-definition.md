# Mira 产品定义

- 状态：Card 与画布版本管理产品基线
- 日期：2026-09-05
- 作用：定义 Mira 解决什么问题、用户如何使用以及产品边界
- 核心原则：**默认从内容开始，也允许先搭计划；走通后再固化方法**

## 1. 一句话定义

Mira 是一块帮助知识工作者把零散材料逐步变成具体成果，也能先搭一个明确的简单计划，并把已经验证过的推进方法沉淀为可复用流程的智能画板。

## 2. 产品命题

知识工作通常从碎片开始，而不是从一份完整流程开始。用户会先收集材料、形成判断、修改成果，直到知道哪些步骤真正有效。要求用户在开始工作前配置 Action、Agent、输入输出或流程图，会把方法设计提前到最不确定的阶段。

Mira 的产品顺序因此是：

```text
材料和想法
  -> 一次局部推进
  -> 可编辑成果
  -> 继续推进并验证方法
  -> 保存为可复用方法
  -> 在新材料上应用并按需生成到目标
```

当用户已经知道要经过哪些步骤时，也可以从计划开始：

```text
明确步骤
  -> 页面内计划草稿
  -> 显式绑定起始内容
  -> 普通 Card 与 Transformation，零 Run
  -> 按需运行、人工调整
  -> 走通后保存为可复用方法
```

两条路径在同一画板汇合。计划不是另一套工作模式或执行引擎；方法仍然只从普通画板中已经验证的工作提取。

## 3. 目标用户

Mira 面向需要独立推进知识成果的人，例如研究者、产品与设计人员、写作者、开发者和学生。他们的共同特征是：

- 输入材料不完整，方向会在工作中变化。
- 需要快速获得第一份可修改的成果。
- 人工判断不能被模型结果静默覆盖。
- 某些有效方法会重复出现，但不值得一开始就编排自动化。

## 4. 核心承诺

1. **内容优先而非强制**：写下材料后即可推进；已经明确步骤时，也可以先搭一个简单线性计划。
2. **局部且明确**：每次只选择当前来源和想得到的下一份成果。
3. **成果可继续工作**：所有模型输出都是普通内容卡的新版本，可以编辑、追溯和继续推进。
4. **人的判断优先**：版本不可变；并发结果不能静默覆盖人工编辑。
5. **方法来自实践**：只有已经走过并确认有效的转化路径，才适合保存为流程模板。
6. **复用不等于后台自动化**：应用方法只铺出计划；用户点击某个下游步骤的`运行到这里`后，Mira 才从上游检查到该步骤，并只生成缺失或来源已变化的成果。

## 5. 用户心智模型

### 5.1 画板 Board

画板是一个课题或项目的工作空间，承载材料、成果以及它们的来路。卡片布局表达当前理解；卡与卡之间唯一的持久联系是转化步骤，不存在无步骤的卡间直连，也不要求画布成为规范流程图。

画板拥有独立于内容对象的生命周期：`active` 用于当前工作，`archived` 用于暂时收起且内容只读、可恢复的课题，`trashed` 用于等待恢复或永久清除的废纸篓项目。archived 仍可在画板管理中重命名、导出、恢复或移入废纸篓；trashed 可恢复、导出或在明确二次确认后永久清除。归档和移入废纸篓都不改写 Card、Version、Transformation、Run 或 WorkflowTemplate；存在活动 Run 或未处理 Candidate 时必须先处理这些状态，不能通过收起画板使 Candidate 不可达。永久清除只接受 trashed Board，删除该 Board 聚合及其 Board 级 Run，不删除全局 WorkflowTemplate、引用文件正文或其他 Board，且不提供撤销。

画板标题可以重命名，但 Board ID 与全部出处引用保持稳定。重命名与生命周期命令以单调 revision 防止跨窗口旧操作覆盖新状态；它们和 Run 启动、导出共享同一画板级互斥边界。active 画板进入普通切换和灵感来源；archived 与 trashed 画板只进入画板管理入口，恢复为 active 后才能继续编辑、生成或作为灵感来源。

画板菜单统一切换与管理入口。`已打开`与`常用`是本机导航偏好，不是 Board 生命周期；关闭只移出已打开列表，不归档、不删除内容，仍可搜索并重新打开。关闭当前画板成功后切到另一个已打开的 active 画板；关闭最后一个时显示未打开画板的空状态，不自动创建新画板。关闭前处理未保存草稿，重新检查活动 Run 与待处理 Candidate，检查失败或仍有待处理工作时保留入口。常用画板独立固定，关闭后仍可由常用入口重新打开。

### 5.2 内容卡 Card

Board 上的 Card 是唯一的画布内容对象。材料、草稿和成果使用同一种卡片；workspace 灵感池独立保存灵感条目，不占用画布位置。“来源”或“成果”由当前关系决定，不是固定卡片类型。

每张卡拥有稳定身份和连续版本，默认展示最新版本。旧版本可查看和恢复，但不会和最新版本同时铺在画布上。

Card 可单独设置名称，用于标题栏、搜索和来源列表辨识。名称属于 Card 元数据，修改或清除名称不改正文、不追加 CardVersion、不影响 stale、Run、Candidate 或本地文件正文，也不进入当前会话正文撤销。未命名时沿用首行或文件名作为显示回退；人工设置的名称不随生成或版本恢复改变。复制、导入导出、备份与画布版本保留名称，不批量迁移旧 Card。

Markdown Card 可以绑定一个工作区内的本地相对路径，作为该 Card 的外部文件投影；一张 Card 最多绑定一个文件，一个文件在同一画板中最多被一张 Card 绑定。Card 及其 CardVersion 仍是唯一真相和历史，文件不是新的内容对象。正文保存、版本恢复、已应用的模型结果或采用 Candidate 产生新 Head 后，Mira 自动将当前 Markdown 写入绑定文件；不会在用户每次输入字符时写文件。

绑定文件被本地程序修改、删除或无法读取时，Mira 不静默覆盖或导入。界面必须显示同步状态，并由用户明确选择用 Mira 当前版本覆盖文件、把本地内容作为新的 human Version 导入 Mira，或解除绑定。file-reference 仍是只读输入材料，不能参与本地文件绑定。

复制和粘贴用于复用当前内容与排布，不用于克隆对象身份。复制多张卡时，Mira 只带走各卡当前 Head、尺寸和组内相对布局；粘贴得到新的独立 Card。原 ID、Version 历史、Transformation、Run 和 Workflow provenance 都不会随之复制。

卡片标题栏用于移动，正文允许原生选字与滚动；文字复制沿用浏览器原生行为，与 Mira 内部的卡片复制分离，不新增系统剪贴板导入或应用级 Clipboard API。阅读、编辑与扩展详情使用同一个 Card 和草稿；来源预览只读，不暗中改变有序选择。正文保存必须使用草稿建立时的 Head 基线，异步 Head 变化不能被提交时的新基线掩盖。

用户可以通过明确命令调整单卡或所选 Card 的尺寸、对齐与间距。尺寸与位置整理一次原子提交、一次会话撤销，字号与内容版本不变；不自动调整未选对象或改变分组归属。旧 Board 几何不因新增界面预设而迁移或截断。

Markdown 编辑器可明确“保存并新建”：先确认当前正文保存成功，再创建下一张相邻、同尺寸的普通空 Card。两次提交不伪装为事务；新建失败不回滚已保存正文，响应不确定时停止并要求核对，不盲目重试创建。离开已创建空卡不自动删除；重复提交不追加相同正文 Version。

Mira 提供有限的当前画板会话历史，用于撤销或重做已提交的 Markdown 正文、Card 位置，以及界面明确记录的 Card 创建和删除。正文撤销仍追加新的 CardVersion；删除撤销只恢复本进程刚删除的原 Card。同一 Bridge 进程仍持有精确批次回执时，页面保留的删除历史不因批次 Card 数量而提前失效；进程重启等原因使回执永久失效时，只失效该条历史并允许继续撤销更早操作。直接记录灵感池不进入 CanvasHistory；只有将灵感添加到当前 Board 形成普通 Card 时，才进入当前 Board 的 create history。切换画板或刷新后历史清空，Transformation、标签、Run、Candidate、计划和方法不进入这套历史。

用户可以为一个稳定画板手动保存命名的`画布版本`。内部对象 `BoardCheckpoint` 保存当时完整、可移植的 BoardArtifact，但它不是自动编辑日志、Board revision 或持久撤销栈。存在活动 Run 或未处理 Candidate 时禁止保存；每个 Board 最多保留 20 个，达到上限时明确要求用户删除，不自动淘汰。查看、比较或恢复画布版本都不覆盖当前 Board；`从这个版本创建副本`始终创建全新 active Board，原画板和检查点保持不变。

### 5.2.1 卡片颜色与分组

用户可以为单张或批量 Card 设置、清除预设颜色。颜色是独立的视觉元数据，不是固定内容类型或执行状态。颜色随普通内容复制保留，不继承组色，也不影响正文、Version、Head、stale、Run、Candidate、标签或文件同步。

用户可把选中的 Card 建为命名的单层分组；每张 Card 最多属于一个组。分组不是内容对象，不拥有正文、版本、模型上下文或执行入口。虚线框由明确成员的包围盒和留白自动生成，不是手绘区域，不支持嵌套、折叠或自动归组。

拖动 Card 无论多远都只改位置，不改归属；拖动期间预览新边界，提交后框贴合成员。拖动框标题整体移动成员及来源和目标全部在组内的转化块，跨组步骤不随动。加入、移出和转组必须通过明确命令，支持批量操作。解组只移除分组元数据，保留 Card、颜色、位置、版本与转化关系。

组标题只选择组，不把成员自动变成模型来源；只有明确选择组内卡片才进入普通有序选择。组名与组色用于标识框，不自动改变成员颜色。普通复制只复制卡片内容、颜色和布局；明确复制整组才创建新的组和 Card 身份，不复制 Transformation 或历史。

颜色、建组、重命名、组色、成员调整、解组和整体移动进入当前 Board 的有限会话历史；不扩大为持久或完整对象图撤销。Card 删除撤销仍只接受同一进程精确回执，并恢复该批删除造成的分组变化，不能覆盖之后的冲突分组编辑。分组与颜色随 Board 导入导出、备份和画布版本保存，旧 Board 缺失这些字段时继续有效。

### 5.3 转化 Transformation

转化表达一次局部推进：**使用这些内容，得到这个成果**。

它包含有序的一张或多张来源卡、恰好一张目标卡，以及成果目标。用户在 Context dock 添加步骤时，一个明确操作只创建转化与空目标卡，保持零 Run；运行永远由用户之后在转化块或关系详情显式点击“运行到这里”启动。底层创建 Transformation 的命令本身始终不创建 Run，来源变化也只提示，不会自动更新下游。

同一组来源也可以由用户在 Context dock 中明确拆成 2–16 个并行方向。用户先在本地草稿中通过`添加分支`增加成果目标，确认后一次性创建这些普通 Transformation 和空目标 Card；它们共享来源但各自独立，不形成新的 Group、Workflow 或计划对象。批量创建必须整批成功或整批失败，并保持零 Run。

画布把 Transformation 显示为来源与目标之间的紧凑`转化块`。转化块不是 Card，不拥有正文、Head 或 Version；它只是现有 Transformation 的可操作投影，用于确认输入顺序、成果目标、运行状态和当前步骤的执行设置。

创建后仍可逐步补充材料：把内容卡连入已有转化块输入端，或从关系详情的`添加来源`选择材料，均只追加有序来源，不另建转化或目标、不自动运行。来源列表支持移除与排序，至少保留一个来源；不得加入目标自身或形成依赖环，活动 Run 与未处理 Candidate 继续阻止来源修改。

每条 Transformation 默认继承宿主当前模型，也可以只覆盖本步骤的模型 ID。模型设置属于 Transformation，不属于来源或目标 Card；同一张 Card 因而可以被不同模型用于不同推进。每次 Run 必须记录实际使用的模型，之后修改步骤设置不能改写历史 Run。

### 5.4 建议 Suggestion

建议是针对当前来源的临时下一步，不是画板节点。它使用成果语言，例如“整理成一页决策”，用户可以忽略建议并直接描述自己的目标。

### 5.5 灵感池 Inspiration Pool

灵感池是 workspace 级的独立记录集合，不依赖任何 Board 或 Canvas。每条灵感有稳定的条目身份、可追加的版本历史和扁平标签；它没有画布坐标、Transformation、Run 或 Board 生命周期。`主意`、`约束`、`技术`、`事件`只是常用标签，一条灵感可以同时拥有多个标签，也允许暂时没有标签。

标签属于灵感条目的可变检索元数据，不属于灵感版本正文。修改标签不会创建 Board CardVersion、标记 Transformation stale、启动 Run 或创建分支。真正需要进入模型上下文的约束、事实或技术说明仍必须写在 Board Card 正文中。

用户可在灵感全文页编辑已有条目的正文与标签。正文变化追加不可变 human 灵感版本；仅标签变化不追加版本，相同内容重复保存不追加版本。保存前检查编辑开始时的 Head 和条目更新时间，冲突保留草稿并要求重新核对。已放到画板的独立 Card、已选定的旧灵感快照均不被静默替换。

用户可以在灵感选择器内直接记录一条 Markdown 灵感，不必切换画板、手动创建 Card 或决定画布位置。记录直接写入 workspace 灵感池并允许零标签保存；它不会改变当前 Canvas、CanvasHistory、Transformation 或 Run，也不会自动加入当前工作集。

已有 Board 上的 Card 不自动迁入灵感池，也不会因为产品语义变化被改写或删除；它们仍是普通 Card，需要进入池时由用户显式重新记录。历史 Board 出处只用于兼容展示，不解析为新的池条目。

用户从 App bar 打开灵感池，通过当前灵感版本正文和标签筛选。筛选和选择只产生页面内候选，不改变 Board。用户按点击顺序挑选结果后，一次性添加到当前画板：

- 每条灵感按所选版本创建一张新的独立 Markdown Card，只复制正文和标签，并保存 `{ poolId, entryId, versionId }` 形式的轻量 `inspirationRef`。
- 新 Card 不共享灵感条目身份、版本历史、Transformation 或 Run；灵感池之后变化不会自动同步或触发运行。
- 整批创建只能全部成功或全部失败。完成后保持用户的选择顺序，并由现有 Context dock 与连接 handle 接管。

`inspirationRef` 只用于查看灵感池出处，不改变 Card、Version、stale 或 Candidate 语义。灵感池条目之后删除或修改后，已放入画板的独立内容仍然可用。

### 5.6 流程模板 WorkflowTemplate

流程模板是一组经过实际使用后保存的、有顺序的转化方法。它记录具名外部输入槽、每一步读取哪些输入槽或上一步成果，以及要得到什么成果；不会复制某次工作的具体正文、卡片身份、坐标、运行状态或模型会话。

“已经使用”在 v1 中有一个可检查的最低标准：路径中每一步的目标 Card 都必须拥有当前 Head，而且 Head 的实际内容非空白、结构可用。这个 Head 可以来自模型，也可以完全由用户写成；Mira 验证的是每一步确实产生过可用成果，而不是要求它必须由 AI 成功运行。

模板适合以下情况：

- 相同方法已经成功走过，并预计会再次使用。
- 步骤顺序稳定，且每一步的输入和预期成果说得清楚。
- 用户希望复用方法，但仍需要在每一步审阅和调整。

不要把一次未验证的猜想直接保存为正式模板。用户可以先继续在画板上试做，确认后再提取。

### 5.7 流程计划 WorkflowPlan

用户可以直接搭计划，或在新材料上应用方法。两种入口都会在当前画板显式铺出一条线性计划：普通 Transformation 和空的目标 Card。计划不是新的内容模型，不独立持久化，也不作为独立运行引擎存在。

确认前的 `PlanDraft` 只存在于当前页面。它由虚线步骤、空目标和输入槽组成；取消、切换 Board 或刷新后消失，不创建 Board 对象、Run 或 WorkflowTemplate。确认后的每一步只携带轻量 `planRef`，用于编号、导航和说明来源，不拥有 Card，也不控制执行。

应用流程满足以下规则：

- 用户从界面的“方法与计划”入口使用模板，把临时方法骨架放到画布；内部步骤顺序已连接，具名外部输入槽保持为空。
- 用户也可以从`搭计划`填写计划名称、最终成果和至少一个有序步骤；最终成果成为最后一步的成果名称。v1 直接计划只要求一个可绑定多张 Card 的`起始内容`槽，后续步骤依次读取上一步成果。
- 用户从内容卡手动连到输入槽；系统不根据当前选择或邻近关系自动猜测绑定。
- 必填槽全部满足数量约束后，用户在第一步节点明确“添加步骤”；触屏和键盘环境可通过槽内“使用已选”完成同一绑定。
- 应用后不启动任何 Run。
- 每一步仍可像普通转化一样查看、修改、运行到这里、重试或删除。
- 每一步可读取上一步目标和具名外部输入；用户可以在执行前调整计划。
- `运行到这里`有明确终点，不越过用户点击的步骤；已经最新的上游成果跳过，空目标或 stale 步骤按依赖顺序生成。
- 计划编号和来源记录为 provenance，便于追溯，但不改变普通对象语义；只有应用已验证方法时才额外写入模板 provenance。

### 5.8 Run 与 Candidate

Run 是某一条 Transformation 的一次执行。开始时冻结来源版本和目标基线。

每个 Run 保留当前公开阶段和最近 20 条按发生顺序排列的公开进度事件，用于回答是否仍在运行、当前阶段、最近发生了什么，以及最终如何结束。事件只保存产品可展示的阶段、短说明、可选脱敏细节和时间；不保存模型思维过程、原始 Prompt、秘密配置、完整工具参数、工具输出或底层会话事件。旧 Run 没有事件列表时仍然有效，界面只显示已有信息，不伪造历史或持续增长的终态耗时。

`运行到这里`在当前页面显示依赖路径中的第 `X/N` 步和成果名。单个 Run 的公开事件在刷新后仍可查看，但整条客户端依赖序列不因此成为新的持久执行对象。运行中的目标 Card 提供直接查看进度和停止入口，用户不需要先进入开发者日志。

若 Run 返回时目标仍处于原基线，结果追加为目标卡的新版本；若目标已被人工编辑或发生其他更新，结果进入 Candidate，等待用户比较、采用或丢弃。

未处理 Candidate 必须一直能从对应 Transformation 到达。用户采用或丢弃它之前，Mira 不允许再次运行、修改或删除这条 Transformation；这避免新的尝试或结构变化把待比较结果藏进不可达的历史文件。

无论单次转化还是流程中的步骤，都使用完全相同的 Run、Version 和 Candidate 安全规则。

### 5.9 分支 Branch

分支代表用户明确选择的另一条方向。只有用户明确从已有内容发起新步骤、创建独立目标时才会出现；应用流程始终铺出无分支的线性计划。

Context dock 的`添加分支`是显式创建 2–16 个方向的快捷入口，不是自动分叉：每个方向都需要用户填写成果目标，确认后独立运行、编辑、版本化和删除。

重新生成、来源变化、Candidate 冲突或应用流程都不得暗中创建分支。Workflow v1 只支持线性步骤，不包含条件分支。

### 5.10 画板导出、备份与导入

`导出画板`用于把一个课题作为版本化 `mira-board` 数据包带走。数据包包含 Board 聚合、属于该 Board 的 Run、非安装型的方法出处快照，以及全部 file-reference Version 的 workspace 相对路径与出现次数；不包含 API Key、当前进程模型设置、窗口状态或 `runtime.rootSessionId`，也不读取、检查或嵌入引用文件正文。

`备份 Mira 数据`使用独立的版本化 `mira-backup` 数据包，覆盖 active、archived 与 trashed Board、全部 Run、全部 WorkflowTemplate、workspace 灵感池和全部 BoardCheckpoint。页面草稿、CanvasHistory、内部剪贴板、日志、秘密配置和 file-reference 指向的实际文件都不属于备份。备份必须在当前写者内取得一致快照；发现活动 Run、损坏成员或无法确认完整性时失败，不能静默跳过后仍宣称成功。旧 V1 备份继续可恢复并按零 Checkpoint 处理。

`导入画板副本`不会 merge 或覆盖现有 Board，而是创建一个新的 active Board，并为包内对象生成一致的新身份映射。当前结构引用必须闭合；合法历史 Run 指向已删除对象以及包外灵感或方法出处时，保留为不解析到本地对象的 opaque 出处，不能碰巧绑定当前 workspace 的同名 ID。导入只接受终态 Run，且方法出处快照不会安装到全局方法库。完整备份恢复不是普通导入：它只面向新建或空 workspace，在 Host 写入该 workspace 前完成 staging、全量校验和切换，不覆盖正在使用的 workspace。

永久清除必须携带用户在 trashed 行上看到的明确确认值和当前 `revision`，服务在 Board 锁内重新读取并确认状态、Run/Candidate 已无活动项，然后以一次可恢复失败的原子提交移除该 Board 文件、其 Board 级 Run 和全部 Checkpoint。任何状态不匹配、确认缺失、活动状态未收敛或部分删除失败都零写入；成功后 Board ID 不得复用。页面历史、备份回执和 Card 删除回执都不是永久清除的恢复入口。

## 6. 核心使用方式

### 6.1 从灵感池组成工作集

1. 用户打开`灵感`；需要捕获时可切到`记录灵感`，直接填写正文和可选标签并保存到 workspace 灵感池。
2. 保存后弹窗继续打开，新记录不自动进入`已选`。用户回到检索，输入关键词或选择一个或多个标签。
3. Mira 只检索灵感条目的当前版本；切换筛选条件不会清掉已经明确挑选的候选。
4. 用户按需要的顺序选择 `1..N` 条灵感，并可在确认前调整顺序或移除。
5. 用户点击`添加到当前画板`；选择作为独立 Card 快照一次写入当前 Board，并保留灵感池出处。
6. 弹窗关闭并聚焦所选内容。用户从内容卡拖线到空白处发起手动新方向，或直接通过 Context dock 创建 Transformation。

关闭或取消未提交的记录草稿不写灵感池；已经明确保存的灵感不会因关闭选择器而回滚。搜索、标签筛选、候选选择和排序仍然零写入，也不会自动连线、生成或启动 Run。

### 6.2 探索和推进

1. 用户写下想法或引用工作区材料。
2. 选择一张或多张卡，检查来源顺序。
3. 选择建议或描述想得到的成果，点击“添加步骤”。
4. 添加步骤只创建 Transformation 与稳定目标卡，保持零 Run；转化块显示“尚未生成”。
5. 用户阅读并编辑结果，或在任一下游步骤明确点击“运行到这里”；Mira 从最上游开始检查，只生成空目标或来源已变化的步骤。
6. 结果可继续作为下一次转化的来源。

若目标 Markdown Card 已绑定本地文件，步骤产生的新 CardVersion 在同一写入边界内尝试自动同步文件。检测到本地文件自上次同步后有变化时，CardVersion 仍保留在 Mira 中，但文件保持原样并进入冲突状态，等待明确处理。

### 6.3 整理和复用画布内容

1. 用户通过框选、追加选择或显式多选入口选中一组 Card。
2. 复制、粘贴或创建副本，保留当前内容、尺寸和组内相对布局；粘贴结果拥有新的身份。
3. 成组拖动或方向键微移时，所选 Card 作为一次整体位置变更保存。
4. 删除前先看到明确的数量并二次确认；若任一卡仍被 Transformation 引用，整批删除拒绝，用户先显式处理相关结构。

页面内复制内容可在不同画板之间粘贴，但只在当前页面会话中有效。它不读写系统剪贴板，也不承诺跨应用复制。

### 6.4 保存有效方法

1. 用户在画板上选中一段已经走通的线性转化路径。
2. Mira 展示将保存的步骤、输入角色和每步成果。
3. 用户检查步骤，并命名模板、补充说明。
4. 保存后，当前画板和历史运行不发生改变。

### 6.5 在新材料上使用方法

1. 用户从“方法”中选择模板并点击“使用”。
2. Mira 显示仅存在于当前页面的计划骨架：步骤、空目标和具名输入槽；此时不写 Board。
3. 用户从内容卡手动连到每个输入槽，或在槽内点击“使用已选”；Mira 不自动绑定。
4. 必填槽满足后，用户在第一步节点点击“添加步骤”，Mira 原子铺出线性 WorkflowPlan，不开始生成。
5. 用户可在任一下游步骤点击“运行到这里”；Mira 按上游依赖顺序检查到该步骤，跳过最新成果并生成需要更新的步骤。

### 6.6 直接搭一个简单计划

1. 用户从`搭计划`填写计划名称、最终成果和有序步骤，可添加、删除或调整顺序；最终成果作为最后一步的成果名称。
2. Mira 把计划作为仅存在于页面内的虚线骨架放到当前画布；此时不写 Board。
3. 用户从内容卡手动连接`起始内容`，或在槽内点击`使用已选`；系统不自动猜测绑定。
4. 用户点击`添加计划`后，Mira 在一次原子写入中创建全部普通 Card 与 Transformation，不创建 Run 或 WorkflowTemplate。
5. 用户在任一步`运行到这里`、编辑或另画分支；全部预定成果走通后，才可按现有验证规则保存为方法。

## 7. 产品结构

Mira 只有一个内容画板、一处 workspace 灵感池和一套安全语义：

- 主工作区：画板，用于创建内容、局部转化和按需生成到目标。
- 灵感池：独立保存可检索的灵感条目，不依赖画板；灵感选择器从中组成有序工作集并放入当前画板。
- 转化块：Transformation 在画板上的紧凑操作入口；点击后配置有序输入、成果目标、验收和当前步骤模型，不产生第二种内容对象。
- 选择工具栏：用于对当前 Card 选择执行颜色、分组整理、复制、粘贴、创建副本和显式删除。
- 计划入口：创建页面内简单线性计划草稿；不是全局模式切换。
- 方法库：管理 WorkflowTemplate，可从画板打开并浏览模板信息。
- 画板管理：统一承载新建、重命名、归档、废纸篓、恢复、画板导入导出和完整备份下载。
- 详情面板：查看关系、版本、运行和流程来源。

产品没有模式切换。工具、模型和权限若未来开放，应作为某一步的执行设置出现，而不是产生第二套产品心智。旧数据归档不属于产品信息架构，必要恢复由产品之外的离线工具完成。

## 8. v1 范围

### 8.1 画布基础操作

必须支持：

- 单选、框选、追加选择和显式多选。
- 当前画板内按当前正文标题、全文或引用文件名/路径搜索 Card；结果展示匹配片段，明确选择后只定位并选中原卡片，不自动打开详情、编辑正文或运行步骤。不检索历史版本、其他画板或引用文件正文。
- 复制当前 Head、尺寸与组内相对布局，并粘贴为新的独立 Card。
- 当前页面会话中的内部剪贴板，可跨画板粘贴。
- 批量创建、移动和删除；每次批量变更只能整体成功或整体失败。
- 删除前二次确认；任一卡被 Transformation 引用时整批拒绝。
- 桌面快捷键和触屏可达的新建、多选入口。
- 桌面画布在非输入或编辑焦点下使用方向键微移选中 Card：默认 `5px`，`Shift + 方向键`为 `20px`；多选时作为一次整体位置变更保存。
- 当前画板会话内有限的撤销/重做：覆盖已提交正文、Card 位置，以及界面记录的 Card 创建和删除；正文操作继续追加 Version。
- 为 Card 添加、移除扁平标签；标签变化不创建 Version，也不影响 stale。
- 在灵感选择器内直接记录 Markdown 灵感到 workspace 灵感池，不切换画板、不要求人工放置，也不自动加入工作集。
- 从 App bar 打开灵感池，按正文与全部所选标签筛选，并原子把选中灵感快照放入当前画板。
- 画布连线只用于发起步骤：从内容卡把手拖线到空白画布可发起手动新方向，落点即新目标卡位置；卡到卡的连线不被接受。

明确不做：

- 卡与卡之间的普通关系连线；画板上不存在无步骤的卡间直连。
- 跨刷新、跨画板或覆盖完整对象图的持久撤销/重做；Transformation、标签、Run、Candidate、Workflow 和模型设置不进入 Card 会话历史。
- 读写系统剪贴板或跨应用复制粘贴。
- 复制 Card ID、完整 Version 历史、Transformation、Run 或 Workflow provenance。
- 标签层级、自动连线、保存搜索、语义向量索引或跨画板实时同步。

### 8.2 Workflow

必须支持：

- 从已存在的线性 Transformation 路径保存模板。
- 模板步骤保留可选模型覆盖；未覆盖的步骤在应用后继续继承当时宿主模型。
- 模板的创建、命名、查看和删除。v1 模板创建后不可编辑；方法变化时回到画板验证并重新提取。
- 使用模板方法骨架，手动绑定具名输入槽，再从第一步节点确认添加步骤。
- 直接创建简单线性计划，手动绑定起始内容，再从第一步节点确认添加计划。
- 显式铺出普通 Card 与 Transformation。
- 保存模板、步骤和本次应用的来源信息。
- 用户可以在任一步启动`运行到这里`：按依赖顺序检查所有上游 Transformation，只运行目标为空或 stale 的步骤，并复用版本、Candidate、失败和停止规则。

明确不做：

- 没有明确目标步骤的全局“一键运行全部”。
- 无人值守执行、刷新页面后的后台续跑或失败后的自动重试。
- 定时器、Webhook、事件触发器和外部队列。
- 条件判断、循环、并行步骤或运行时动态分支。
- 根据输出自动选择下一步。
- 流程市场、团队权限和发布审批。
- 独立的 Action、executor、tool 或 chain 画布。
- 把转化块保存成 Card，或为它建立独立正文、Head、Version 和隐藏会话身份。

### 8.3 Board 生命周期与可移植数据

必须支持：

- 重命名 active 或 archived Board，不改变稳定 ID、内容、结构、Run 或出处。
- 在 active、archived 与 trashed 之间执行受门禁保护的归档、移入废纸篓和恢复；对 trashed Board 提供明确二次确认的永久清除；普通工作入口只展示 active Board。
- 导出单个 Board 的版本化数据包，并把同一数据包重复导入为互相独立的副本。
- 备份全部 Mira 管理数据，并只向新建或空 workspace 恢复完整备份。
- 手动保存、命名、预览、比较、导出和删除画布版本，并从任一画布版本创建独立 Board 副本。
- 完整备份包含全部画布版本；旧版备份仍可恢复并按零画布版本处理。
- 所有导入先完成大小、格式版本、schema、数量、引用完整性和身份映射校验；失败时生产列表零可见写入。

明确不做：

- 从当前产品直接读取 legacy v1 归档，或把 `cards/restore` 当作导入入口。
- 在正在使用或已有数据的 workspace 上覆盖式恢复完整备份。
- 默认把 file-reference 指向的文件正文、API Key、进程模型设置或任意 workspace 文件装入数据包。
- 导出和备份不携带 Markdown Card 的本地文件绑定元数据；绑定必须在目标 workspace 中重新建立，避免导入时意外写入本机文件。
- 在未处于 trashed、未二次确认或存在活动 Run/Candidate 时物理清除 Board；永久清除不提供撤销，也不删除其他 Board 或全局 WorkflowTemplate。
- 自动为每次编辑、移动或 Run 保存画布版本，或用画布版本原地覆盖、合并、rebase 当前 Board。

## 9. 不变量

1. 一次 Transformation 使用有序的 `1..N` 个来源，得到一个目标。
2. 创建 Transformation、直接创建或应用 WorkflowPlan、来源变更都不会自行创建 Run；只有用户明确选择“生成”或点击`运行到这里`才启动 Run。
3. 画板默认展示每张 Card 的最新版本。
4. 重新生成只追加同一目标 Card 的版本，不自动创建分支。
5. Run 冻结来源；结果写回必须通过目标基线比较。
6. 人工 Head 发生变化时，模型输出只能成为 Candidate。
7. Workflow 中的产物仍是普通 CardVersion，不存在另一种“流程产物”。
8. WorkflowTemplate 不拥有用户项目内容，删除模板不删除任何已应用计划。
9. 直接创建或应用 Workflow 只铺计划，不执行任何步骤；直接计划不会自动创建 WorkflowTemplate。
10. 所有结构分支都必须由用户明确创建。
11. 未处理 Candidate 必须先采用或丢弃，才能重跑、修改或删除对应 Transformation。
12. 粘贴只复制当前 Head 内容、尺寸和相对布局，所有对象身份、历史与图结构保持独立。
13. 批量创建、移动或删除 Card 不得产生部分写入；任一删除目标仍被结构引用时整批拒绝。
14. `运行到这里`不得越过用户选择的目标；任一步 Candidate 未处理、运行失败、被停止或来源不可用时，后续步骤不得启动。
15. PlanDraft 不持久化；`planRef` 只分组和追溯，不拥有 Card、Transformation 或运行状态。
16. 标签变化不创建 CardVersion，不改变 Head/digest，也不触发 stale、Run 或分支。
17. 灵感筛选与候选选择零写入；只有用户明确点击`保存灵感`或`添加到当前画板`才写入灵感池或当前 Board。记录独立于画板且不进入工作集；批量放入保持零部分写入。
18. 会话历史不得原地改写 Version 或绕过结构引用检查；删除恢复只接受当前进程保存的精确回执，刷新或切换 Board 后不可继续。直接记录到灵感池不进入 CanvasHistory；添加到当前 Board 才产生普通 Card 创建历史。
19. Board 归档、移入废纸篓和恢复只改变生命周期元数据；活动 Run 或未处理 Candidate 存在时不得隐藏该 Board。
20. 导入画板只创建全新且引用闭合的对象身份，不 merge、不覆盖，也不复用会话删除回执。
21. 导出与备份不携带秘密配置或 file-reference 正文；完整备份恢复不覆盖正在使用的 workspace。
22. Board 永久清除只接受 trashed 状态和显式确认，在同一原子提交中移除 Board 聚合及其 Board 级 Run；成功后不可撤销且 ID 不复用。
23. 每个 Node-backed 可写 Host 必须先取得 workspace 级独占写锁；已有其他写者时启动 fail-closed，不得以部分只读或覆盖模式继续。没有原子锁适配器的 DSH/Cordis 宿主仍必须遵守单写者约束，不能宣称获得跨进程锁保护。
24. 卡与卡之间唯一的持久结构联系是 Transformation；不存在无步骤的卡间直连，旧数据中的普通关系字段在读取与导入时静默忽略。
25. 本地文件绑定只允许 Markdown Card 与 workspace-relative 路径；一次只绑定一个文件。自动同步前必须比较上次同步基线，外部变化只能进入显式冲突处理；同步失败不得回滚或删除已追加的 CardVersion。
26. BoardCheckpoint 只能由用户为无活动 Run、无未处理 Candidate 的 active Board 手动创建；每 Board 最多 20 个且不得静默淘汰。
27. 从 BoardCheckpoint 恢复只创建全新 active Board 副本，不覆盖原 Board；BoardArtifact 不携带 Checkpoint，MiraBackup 必须完整携带并恢复 Checkpoint。

## 10. 成功标准

- 新用户能在五分钟内从一张材料卡得到第一份可编辑成果。
- 用户能正确判断一次转化会读取哪些卡片和版本。
- 用户会修改成果并继续推进，人工内容静默丢失次数为零。
- 重复完成一段方法后，用户能理解“保存为方法”的价值。
- 应用模板前，用户能预测会铺出哪些步骤；应用后不会误以为系统已开始运行。
- 直接搭计划前，用户能预测会创建哪些步骤；添加后能确认这些步骤尚未运行。
- 用户可以在任一步停下、修改或退出，而不会破坏已完成成果。
- 用户不需要理解 Action、input/output、executor 或 chain。
- 用户能成组整理和跨画板复用当前内容，而不会误以为复制了历史、关系或流程来源。
- 用户能收起、恢复、重命名和永久清除课题，并明确区分归档、废纸篓与不可撤销的永久清除。
- 用户能判断画板导出、Mira 数据备份和完整恢复分别包含什么，不会误以为 file-reference 正文或 API Key 已被备份。
- 用户可以把 Markdown Card 绑定到一个本地文件，正常保存后无需额外点击即可看到文件更新；外部修改时能明确区分 Mira 版本与本地版本，并把本地修改作为新的历史 Version 保留下来。
- 用户能明确区分 CardVersion、当前会话撤销和画布版本，并可从命名画布版本创建独立副本继续工作。
